# Design: Sim Zed 1.16 port audit

## Overview

The audit treats the port as two tree deltas anchored at immutable refs:
`v1.10.2` to `sim-dev`, and `v1.16.1` to the rebased branch. This is necessary
because `sim-dev` is rooted in a separate Git history and has no merge base with
the local upstream tag. Commit and range evidence is retained as supporting
context, but the completeness ledger is path- and content-based.

## Decisions

### D1: Compare immutable tree deltas

- Choice: Generate a ledger from old-base/old-tip and new-base/new-tip trees.
- Rationale: Tree comparison remains well-defined when ancestry and patch IDs do
  not. It can account for squashed and rewritten commits.
- Alternatives considered: A literal `git range-diff v1.10.2..sim-dev
  v1.16.1..HEAD` treats the unrelated Sim root and all of its history as a patch
  series, producing no trustworthy one-to-one mapping.
- Consequences: Exact files and path-level adaptations are mechanically auditable;
  semantic behavior still requires specification, test, and launch evidence.

### D2: Repair incrementally from Cargo metadata outward

- Choice: Re-run Cargo after each minimal dependency or API correction, preserving
  the upstream v1.16.1 form unless Sim behavior requires an adaptation.
- Rationale: The first manifest parse failure masks later compiler diagnostics.
- Alternatives considered: Bulk-copying old manifests would overwrite newer
  upstream dependencies and features.
- Consequences: Each change has a direct diagnostic and old/new source comparison.

### D3: Use layered functional evidence

- Choice: Combine ledger classification, manifest validation, focused tests,
  runnable-target checks, and an application startup attempt.
- Rationale: Compilation cannot prove UI, persistence, service, or workflow parity.
- Alternatives considered: Exhaustively exercising every imported feature is not
  locally feasible and would conflate this port audit with unfinished work in the
  imported feature specifications.
- Consequences: The handoff explicitly identifies unverified behavior instead of
  overstating parity.

### D4: Reconcile dependencies from upstream declarations

- Choice: For any dependency declaration present in v1.16.1, restore the complete
  upstream declaration before resolving Sim additions or regenerating the lockfile.
- Rationale: A tree transplant must not silently redirect upstream dependency
  trust, compatibility, or platform behavior to a fork.
- Alternatives considered: Keeping Sim fork substitutions until compilation
  fails does not demonstrate that fork-only behavior is required and obscures
  dependency provenance.
- Consequences: Any proposed fork becomes a separately evidenced and approved
  exception. New Sim crates may add dependencies, but may not override upstream
  identities by default.

### D5: Keep icon variant and asset stems identical

- Choice: Rename the eleven existing Zed-named SVG files to the snake-case stems
  generated by their Sim-branded `IconName` variants, preserving file contents.
- Rationale: `IconName::path` deterministically maps each enum variant to
  `icons/{snake_case_variant}.svg`; changing only the enum therefore makes the
  existing artwork unreachable at runtime.
- Alternatives considered: Special-casing aliases in `IconName::path` would
  preserve mismatched branding identifiers and weaken the existing exhaustive
  asset tests.
- Consequences: All Sim icon variants resolve normally, while the icon tests
  continue to enforce both missing-asset and dangling-asset invariants.

### D6: Apply the asset-stem contract to vector images

- Choice: Rename the two Zed-named vector SVGs to the snake-case stems generated
  by `SimLogo` and `SimXCopilot`, preserving their contents, and replace the stale
  single-path assertion with exhaustive inventory tests.
- Rationale: `VectorName::path` uses the same deterministic snake-case convention
  as icons, but the old test encoded the mismatched filename and therefore hid
  the incomplete branding port.
- Alternatives considered: Mapping Sim variants back to Zed filenames would keep
  the asset identifiers inconsistent and allow the same defect for future vector
  additions.
- Consequences: The welcome, onboarding, and vector preview surfaces resolve both
  Sim vectors normally, and tests enforce the mapping in both directions.

### D7: Restore upstream asset identity and separate future branding

- Choice: Supersede D5 and D6 by restoring every existing `assets/` path and blob,
  every `IconName` and `VectorName` identity, and every related call site to its
  exact v1.16.1 form. Retain only asset files absent from v1.16.1 as separately
  inventoried Sim additions.
- Rationale: Renaming an upstream enum and its asset together makes the build
  coherent but still replaces upstream identity. Sim branding must be introduced
  later as explicit new assets rather than by taking over Zed-owned paths.
- Alternatives considered: Aliasing Sim variants to Zed paths preserves neither
  enum nor reference identity and was explicitly rejected by the maintainer.
- Consequences: Existing assets are mechanically comparable with v1.16.1, while
  future branding work has a clear additive boundary.

## Components and flow

1. Resolve and record comparison refs and ancestry facts.
2. Generate the old and new path deltas and classify their relationship.
3. Inspect unresolved or adapted build-critical paths against all four trees.
4. Restore all existing Zed dependency declarations from v1.16.1, layer only
   Sim-only additions, and regenerate the lockfile.
5. Repair one confirmed source defect at a time and rerun Cargo metadata/checks.
6. Validate representative Sim-specific crates and startup paths, then record
   residual manual-verification needs.

Existing icon and vector assets follow the v1.16.1 enum and snake-case path
contract. D5 and D6 record the superseded approach; D7 restores the upstream
identities and keeps new Sim assets in distinct files. Exhaustive tests continue
to validate both directions of each enum-to-asset mapping.

The macOS validation host has Xcode selected but does not have the separately
downloadable Metal command-line toolchain. The port therefore exposes upstream's
existing `gpui_platform/runtime_shaders` path as the non-default Zed feature
`runtime-shaders`. Normal upstream shader-build behavior remains unchanged, while
`ZED_STATELESS=1 cargo run -p zed --features runtime-shaders,rust-tools` provides
an isolated startup check that does not interfere with an installed stable Zed
instance.

## Failure and recovery

The audit never mutates refs or rewrites history. A missing ref stops ledger
generation with a clear error. Build failures are retained as evidence and are
fixed only when comparison to the old Sim and newer upstream trees shows they are
port-induced. Environment-specific launch failures are reported separately from
code failures.
