# Requirements: CI/CD Archived Workflow Migration

## Problem

At the measured Phase 1 starting point, the repository had 41 active top-level GitHub Actions workflow files. Only `run_tests.yml` and `release.yml` belong to the intended minimal CI/CD surface; the other 39 workflows were active and had to be archived before any restoration plan could be accurate or safe. Several of those workflows are generated by `cargo xtask workflows`, so moving YAML files alone would allow the generator to reactivate them.

## Scope

### In scope

- Audit the actual top-level workflow inventory.
- Archive every top-level `.github/workflows/*.yml` file except `run_tests.yml` and `release.yml`.
- Keep archived generated workflows excluded from active xtask output.
- Document the exact archive inventory and later restoration requirements.
- Preserve later restoration phases without performing them during Phase 1.

### Out of scope

- Restoring or activating any archived workflow during Phase 1.
- Changing the behavior of `run_tests.yml` or `release.yml` beyond deterministic regeneration.
- Deploying, releasing, configuring secrets, or triggering archived automation.
- Reimplementing `push_release_update_notification`, which remains part of `release.yml`.

## Glossary

- **Active workflow**: A `.yml` file directly under `.github/workflows/`, where GitHub Actions discovers it.
- **Archived workflow**: A workflow moved to `.github/workflows/archive/`, which GitHub Actions does not discover.
- **Core workflow**: One of the two retained active workflows, `run_tests.yml` or `release.yml`.
- **Generated workflow**: A workflow with the header `# Generated from xtask::workflows::` and a Rust source in `tooling/xtask/src/tasks/workflows/`.
- **Active allowlist**: The exact set `{run_tests.yml, release.yml}` during Phase 1.

## Requirements

### Requirement 1: Archive the actual non-core workflow inventory

**User story:** As a maintainer, I want the migration to start from the repository's measured workflow inventory, so that no active workflow is omitted or incorrectly treated as already archived.

#### Acceptance criteria

1. **1.1** THE Phase 1 baseline SHALL record 41 top-level `.github/workflows/*.yml` files, consisting of 2 retained core workflows and 39 non-core workflows.
2. **1.2** WHEN Phase 1 completes, THE repository SHALL contain only `run_tests.yml` and `release.yml` as top-level `.github/workflows/*.yml` files.
3. **1.3** WHEN a non-core workflow is archived, THE migration SHALL move it with Git history preserved and SHALL retain its content under `.github/workflows/archive/`.
4. **1.4** THE archive README SHALL list exactly the 39 archived workflow filenames once each.
5. **1.5** THE Phase 1 migration SHALL NOT restore or activate any archived workflow.

### Requirement 2: Keep generated archived workflows inactive

**User story:** As a developer running `cargo xtask workflows`, I want archived generated workflows to remain archived, so that regeneration cannot silently expand the active CI surface.

#### Acceptance criteria

1. **2.1** WHEN `cargo xtask workflows` runs, THE generator SHALL write only `run_tests.yml` and `release.yml` as active Zed workflows.
2. **2.2** WHEN `cargo xtask workflows` runs, THE generator SHALL NOT modify, remove, or recreate any workflow under `.github/workflows/archive/`.
3. **2.3** THE `ARCHIVED_ZED_WORKFLOWS` policy SHALL include every generated Zed workflow archived in Phase 1 and SHALL exclude both retained core workflows.
4. **2.4** WHEN generator policy is tested, THE test SHALL fail if a Zed workflow is neither in the active allowlist nor the archived generated set.

### Requirement 3: Restore on-demand bundling in a later phase

**User story:** As a developer, I want to trigger a full multi-platform bundle build by applying a label to a pull request, so that I can verify release artifacts before merging.

#### Acceptance criteria

1. **3.1** WHEN a pull request is labeled `run-bundling`, THE restored workflow SHALL build and upload Linux, macOS, and Windows bundles for aarch64 and x86_64.
2. **3.2** WHEN a labeled pull request is synchronized, THE restored workflow SHALL rebuild its bundles.
3. **3.3** WHEN bundle jobs complete, THE restored workflow SHALL upload their release artifacts.
4. **3.4** IF the `run-bundling` label is removed, THE restored workflow SHALL NOT cancel already running jobs because of the removal event.

### Requirement 4: Restore nightly releases in a later phase

**User story:** As a release manager, I want scheduled nightly builds, so that users can test recent changes without waiting for a formal release.

#### Acceptance criteria

1. **4.1** WHEN the four-hour schedule triggers, THE restored workflow SHALL determine whether a new nightly tag is needed.
2. **4.2** IF a new nightly is needed, THE restored workflow SHALL run tests, build all platform bundles, and upload them to DigitalOcean Spaces.
3. **4.3** WHEN a nightly succeeds, THE restored workflow SHALL update the nightly Git tag.
4. **4.4** IF a nightly fails, THE restored workflow SHALL notify Slack.

### Requirement 5: Restore post-release automation in a later phase

**User story:** As a release manager, I want post-release tasks to run automatically, so that published releases reach downstream systems consistently.

#### Acceptance criteria

1. **5.1** WHEN a GitHub Release is published, THE restored workflow SHALL refresh the cloud releases page.
2. **5.2** WHEN a GitHub Release is published, THE restored workflow SHALL deploy documentation to the appropriate preview or stable channel.
3. **5.3** WHEN a GitHub Release is published, THE restored workflow SHALL post a Discord announcement.
4. **5.4** WHEN a GitHub Release is published, THE restored workflow SHALL publish the Windows package to Winget.
5. **5.5** WHEN a GitHub Release is published, THE restored workflow SHALL create a Sentry release.
6. **5.6** IF a post-release step fails, THE restored workflow SHALL notify Slack.

### Requirement 6: Restore collaboration server deployment in a later phase

**User story:** As an infrastructure engineer, I want tag-driven collaboration server deployment, so that production updates remain controlled and repeatable.

#### Acceptance criteria

1. **6.1** WHEN a `collab-production` tag is pushed, THE restored workflow SHALL run style checks and tests.
2. **6.2** WHEN validation succeeds, THE restored workflow SHALL build and publish a Docker image to DigitalOcean Container Registry.
3. **6.3** WHEN the image is published, THE restored workflow SHALL deploy it to the production Kubernetes cluster.

### Requirement 7: Restore documentation automation in a later phase

**User story:** As a documentation maintainer, I want documentation workflows restored deliberately, so that builds, deployments, and suggestions use reviewed dependencies and channels.

#### Acceptance criteria

1. **7.1** WHEN a push to `main` occurs, THE restored nightly documentation workflow SHALL build the mdBook documentation.
2. **7.2** WHEN the nightly documentation build succeeds, THE restored workflow SHALL deploy it to the Cloudflare Pages nightly channel.
3. **7.3** WHEN a release is published, THE restored reusable documentation workflow SHALL deploy the appropriate preview or stable channel.
4. **7.4** WHEN documentation suggestions are enabled for a pull request, THE restored workflow SHALL provide its configured suggestion feedback without activating unrelated archived workflows.

### Requirement 8: Restore pull-request autofix in a later phase

**User story:** As a developer, I want dispatched automated fixes, so that common CI failures can be corrected consistently.

#### Acceptance criteria

1. **8.1** WHEN dispatched with a pull request number, THE restored workflow SHALL run cargo fix, Clippy fixes, cargo-machete fixes, Prettier, and cargo fmt.
2. **8.2** IF those tools change files, THE restored workflow SHALL commit and push the changes to the pull request branch.

### Requirement 9: Restore Nix builds in a later phase

**User story:** As a Nix user, I want label-triggered Nix builds, so that Linux and macOS derivations are verified before merge.

#### Acceptance criteria

1. **9.1** WHEN a pull request is labeled `run-nix` or `run-bundling`, THE restored workflow SHALL build the Nix derivation for Linux and macOS.
2. **9.2** WHEN a Nix build completes, THE restored workflow SHALL push its results to Cachix.

### Requirement 10: Restore compliance checks in a later phase

**User story:** As a compliance officer, I want scheduled compliance reports, so that release readiness is reviewed before tagging.

#### Acceptance criteria

1. **10.1** WHEN the Tuesday 17:30 UTC schedule triggers, THE restored workflow SHALL check the latest preview tag.
2. **10.2** WHEN the check completes, THE restored workflow SHALL upload a compliance report artifact.
3. **10.3** IF the check fails, THE restored workflow SHALL notify Slack.

### Requirement 11: Restore extension automation in a later phase

**User story:** As an extension developer, I want extension testing, versioning, and publication restored as a coherent group, so that cross-workflow dependencies remain valid.

#### Acceptance criteria

1. **11.1** WHEN an extension directory changes in a pull request, THE restored workflows SHALL run Rust checks and extension validation.
2. **11.2** WHEN an extension version changes, THE restored workflows SHALL verify the bot-managed version bump.
3. **11.3** WHEN the extension CLI is tagged, THE restored workflows SHALL build it, upload it, and update dependent repository references.
4. **11.4** WHEN an extension is ready to publish, THE restored workflows SHALL bump its version and create a release pull request.

### Requirement 12: Restore Danger checks in a later phase

**User story:** As a maintainer, I want Danger checks on pull requests and merge queue entries, so that common quality problems are reported automatically.

#### Acceptance criteria

1. **12.1** WHEN a pull request targeting `main` is opened or synchronized, THE restored workflow SHALL run Danger checks.
2. **12.2** WHEN a merge queue entry is created, THE restored workflow SHALL run Danger checks.

### Requirement 13: Restore pull-request and issue labeling in a later phase

**User story:** As a community manager, I want author-type labels applied automatically, so that triage remains consistent.

#### Acceptance criteria

1. **13.1** WHEN a pull request is opened, THE restored workflow SHALL apply the configured author label.
2. **13.2** WHEN an issue is opened by an eligible community champion, THE restored workflow SHALL apply the configured community champion label.

### Requirement 14: Restore release-branch cherry-picks in a later phase

**User story:** As a release manager, I want dispatched cherry-picks, so that reviewed fixes can be backported consistently.

#### Acceptance criteria

1. **14.1** WHEN dispatched with a commit SHA, target branch, and channel, THE restored workflow SHALL cherry-pick the commit and push the target branch.

### Requirement 15: Restore automated version bumping in a later phase

**User story:** As a release manager, I want version bumps automated, so that main, preview, stable, and collaboration staging changes follow a consistent process.

#### Acceptance criteria

1. **15.1** WHEN a version-bump workflow is dispatched, THE restored workflow SHALL compute the next version and create the configured branches or tags.

### Requirement 16: Restore community management in a later phase

**User story:** As a community manager, I want issue and pull-request maintenance automation restored deliberately, so that repository organization improves without unreviewed activation.

#### Acceptance criteria

1. **16.1** WHEN an issue becomes stale, THE restored workflow SHALL warn and later close it according to policy.
2. **16.2** WHEN a potential duplicate issue is detected, THE restored workflows SHALL comment, measure effectiveness, and maintain duplicate magnets.
3. **16.3** WHEN a community pull request is opened or refreshed, THE restored workflows SHALL synchronize the community pull-request project.
4. **16.4** WHEN a good-first-issue label is added, THE restored workflow SHALL notify eligible first-time contributors.
5. **16.5** WHEN issue-ranking maintenance runs, THE restored workflows SHALL update the configured all-time or weekly rankings.
6. **16.6** WHEN auxiliary community events occur, THE restored workflows SHALL perform their configured blank-issue, congratulations, closed-issue, and triage synchronization actions.

### Requirement 17: Restore Slack notifications in a later phase

**User story:** As a team member, I want operational Slack notifications restored only after their secrets and destinations are verified, so that important events reach the correct responders.

#### Acceptance criteria

1. **17.1** WHEN a hotfix is merged without post-merge review, THE restored workflow SHALL notify the pull-request review operations channel.
2. **17.2** WHEN configured community automation fails, THE restored workflow SHALL notify the appropriate Slack channel.
3. **17.3** WHEN a high-priority label is created or first responders must be paged, THE restored workflows SHALL notify the configured responders.

## Constraints

- Phase 1 must use `git mv` for every archived workflow.
- Phase 1 must preserve unrelated worktree changes and must not commit.
- Archived workflows remain inert until their explicit later task is authorized and completed.
- Restoration tasks must remove generated workflows from `ARCHIVED_ZED_WORKFLOWS` when reactivating them.
