# Design: Rustlings CI and release

## Overview

The active workflow entry points will be replaced with small, fork-oriented job graphs while the larger helper library remains available to archived workflows. CI becomes one Linux job. Release becomes three independent platform bundle jobs followed by one publishing job. Existing bundle scripts remain the source of platform packaging behavior and receive only the stable Rustlings naming changes needed for installable artifacts.

## Existing context

Both active YAML files are generated by `tooling/xtask/src/tasks/workflows.rs`. The current `run_tests()` and `release()` functions assemble many jobs that depend on Simtropolis runners and services. The platform bundle scripts accept catalog-selected application features, including `multiplayer-tools` and `rust-tools` for the Rust product, and degrade to unsigned or ad-hoc-signed output when signing variables are absent.

Archived generated workflows import helpers from `release.rs`, `run_tests.rs`, and `run_bundling.rs`. Removing those helpers would broaden the change and break generator compilation, so only active entry-point composition and new focused helpers will change.

## Design decisions

### Active CI composition

- Responsibility: Define one Linux validation job and the three requested triggers.
- Integration: Reuse pinned checkout and cargo-nextest setup steps plus the repository Linux dependency scripts.
- Rationale: One job is the smallest graph satisfying all requested checks and avoids private cache or service dependencies.

### Active release composition

- Responsibility: Build the three requested target bundles, normalize them to Rustlings artifact filenames, and publish them only after all builds succeed.
- Integration: Invoke `script/bundle-linux --rust-tools`, `script/bundle-mac --rust-tools aarch64-apple-darwin`, and `script/bundle-windows.ps1 -RustTools -Architecture x86_64`. Use pinned upload/download artifact helpers and `gh release create` or `gh release upload` against the current repository.
- Rationale: Dedicated jobs make platform failures isolated and let the publish job express an explicit dependency barrier without a more complex matrix-output protocol.

### Stable packaging branding

- Responsibility: Display Rustlings in stable installers and produce Rustlings-named platform packages.
- Integration: Change stable macOS bundle metadata, Linux desktop metadata/archive naming, and stable Windows installer definitions while retaining internal `zed` binary paths.
- Rationale: This distinguishes installed release builds without a risky crate, binary, URL-scheme, IPC, or broad UI rename.

### Signing behavior

- Responsibility: Keep development releases buildable with no external signing credentials.
- Integration: Preserve the bundle scripts' existing conditional signing checks and omit signing secret environments from the active workflow.
- Rationale: Missing credentials should result in unsigned/ad-hoc artifacts, not fabricated credentials or a failed fork release.

## Testing strategy

- Validate this canonical spec before implementation and after evidence updates.
- Run generator unit tests and `cargo xtask workflows`.
- Run the repository workflow validation invoked by generation, plus focused action checks if available.
- Run bundle-script dry-run modes to confirm the selected `agentic` defaults and explicit Rust tooling features without performing expensive platform builds locally.
- Parse and inspect generated YAML for triggers, permissions, job dependencies, runners, commands, artifact names, and forbidden organization-specific references.
