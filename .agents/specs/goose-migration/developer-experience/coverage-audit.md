# Developer Context and Commands Coverage Audit

## Audit scope and method

This audit traces observable Goose behavior through implementation, call sites, protocol schemas, desktop and CLI consumers, configuration, persistence, tests, feature flags, security boundaries, failure paths, and cleanup before mapping it to Sim. Goose is evidence, not a compatibility architecture. The detailed inventory below is the domain catalog for `Developer Context and Commands`; the migration-wide summary is updated in `../coverage-catalog.md`.

Inspected Goose roots include:

- `projects/goose/crates/goose/src/agents/execute_commands.rs`, `agents/state_machine/`, `slash_commands/`, `agents/prompt_manager.rs`, and command tests.
- `projects/goose/crates/goose/src/hints/`, `source_roots.rs`, `sources.rs`, `execution/manager.rs`, and their tests.
- Relevant `projects/goose/crates/goose/src/acp/server/` session, slash-command, source, resource, tool, app, proxy, prompt-run, cancellation, and cleanup handlers; `projects/goose/crates/goose/src/acp/response_builder.rs`; and `projects/goose/crates/goose-sdk-types/src/custom_requests.rs`.
- `projects/goose/crates/goose-cli/src/session/`, CLI configuration/serve paths, desktop autocomplete/settings/source/skill/MCP App surfaces, manifests, documentation, and feature flags reached from those implementations.
- Sim's complete native integration path in `crates/agent`, `crates/acp_thread`, `crates/agent_ui`, `crates/agent_settings`, `crates/prompt_store`, `crates/project`, `crates/context_server`, `crates/settings_ui`, and persistence tests.

The classifications in this file are mutually exclusive and use the requested wording. “Equivalent” means equivalent observable Sim behavior, not matching names or data structures.

For compactness, unprefixed Goose Rust paths in the tables are relative to `projects/goose/crates/goose/src/`; `CLI` paths are relative to `projects/goose/crates/goose-cli/src/`; `desktop` paths are relative to `projects/goose/ui/desktop/src/`. All Sim paths are repository-relative and name the owning symbol where one exists.

## Pre-repair gaps and incorrect assumptions

The prior pack missed or overclaimed the following source-backed facts:

1. Goose's built-in agent inventory is exactly `prompts`, `prompt`, `compact`, `clear`, `skills`, `doctor`, `goal`, `grind`, and `status`; `/help` is CLI-local, and no literal agent `/recipe` exists.
2. Sim already gives users stronger unknown-command behavior in `MessageEditor`; inventing a second rejection in `NativeAgentConnection` would change direct ACP compatibility without Goose evidence.
3. Sim advertised only zero- and one-argument MCP prompts and silently omitted prompts with multiple arguments. The repaired pack now closes that confirmed gap through the existing catalog/dispatcher.
4. Clear must not erase Sim's `ActionLog` or other records of real edits. Goose only demonstrates clearing conversation and usage.
5. Goose hints add nested access-triggered loading and recursive imports beyond Sim's root context, but their silent diagnostics and lexical cycle tracking are not safe templates. Both behaviors are decision-gated rather than assumed.
6. Goose `sources.rs` is typed filesystem CRUD/import/export, not a speculative path registry. Sim project and skill behavior is already native; any public source API is a separate decision.
7. `NativeAgent::pending_sessions` already coalesces loads and existing tests prove shared live state/reference counts. Only failure/removal/retry regression coverage was unconfirmed.
8. Sim already has a Skills settings surface. Migration catalog row DUI-010's “management UI not verified” statement was too broad.
9. The old developer-experience MCP App requirements duplicated conditional desktop/type-SDK work and lacked an approved threat model. They remain outside this feature.

## Decisions requiring review

1. Whether Sim should support nested, path-access-triggered instruction loading and, if so, its precedence, lifetime, trust, ignore, remote-worktree, and diagnostic semantics.
2. Whether Sim should define instruction-file import syntax. Approval must precede a spec for canonical containment, ignored files, canonical cycle detection, depth/operation/byte budgets, precedence, and visible diagnostics.
3. Whether Sim needs a public source CRUD/import/export API for skills, projects, agents, or checks, and which existing owner authorizes each mutation.
4. Whether Goose-style agent/check catalogs and additional read-only distribution roots are Sim products.
5. Whether MCP Apps are approved at all; if so, approve the metadata trust model, renderer/origin, CSP, bridge permissions, egress/navigation/download/clipboard policy, cache/retention, and single implementation owner.

No remaining decision above is made by this specification. Persistent `/goal` and bounded `/grind` were separately approved and are owned by `.agents/specs/goose-migration/goal-grind-commands`.
